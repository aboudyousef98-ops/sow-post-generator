§1

The one insight that shapes everything

All four asks collide on the same missing piece: the server does not know who is calling it.

  • Every function checks only two things: the request came from an allowed origin (a browser header any program can fake) and the shared path token — which ships inside the public JS bundle and is documented in the code itself as "not a secret".
  • Admin vs member is checked only in the browser. The server never reads a role.
  • GET /users hands every caller the whole roster including password salts and hashes — because login verification happens in the browser.
  • "Last updated by" is free text the client sends. Anyone can write as anyone.
Consequence: the bot can't authenticate (item 1 of your spec), extra-work privacy can't be enforced, and notifications can't be targeted — for the same reason. So the plan builds one server-side identity mechanism (per-user API tokens) and lets all four features ride it. That turns four separate projects into one foundation + four thin layers.
§2

How the system works today (audit result)

Browser (React SPA)⟷ 15s poll, whole blobs 12 Netlify Functions⟷ merge + etag CAS Netlify Blobs: board · records · users · ahjs · extrawork
SOW Bot (Grok, real browser)⟶ clicks the UI like a human — no API lane exists
  • Storage model: whole-collection GET / whole-collection PUT with a server-side merge — newer updatedAt wins per row, deletes are tombstones, 5 retry rounds on write conflict. Useful discovery: PUT-ting a single project already upserts just that row — the bot API can be a thin documented wrapper over this, not a storage rewrite.
  • Audit log already exists: every board edit writes a {field, old, new, who, when} activity entry — append-only and immutable on the server, capped at 5,000. Your item 4 (history + undo) extends this instead of inventing a new log.
  • Cost problem, measured: the 15-second poll downloads the full board — 847 KB per poll ≈ 170 GB/month. The ETag fix (server says "nothing changed", 304, ~0 bytes) is fully designed and was deferred only because it collided with work that is now committed. It should ride in this package.
  • No cron, no webhooks, no push — the server only ever answers; it never initiates.
  • The bot already left fingerprints: the automations system has an exceptActors option that exists because sow_bot's new rows kept auto-assigning themselves to it. The board-export CSV was built "for the bot's two standing jobs". The app is already half-aware of the bot — this plan makes it a first-class citizen.
Two facts that change your spec slightly: ① Address is not on board rows (it lives on Compose records) and install date is derived from records — the read API will join records server-side and return them read-only. ② "Section" (Pre-Design / Review / …) is not a field — it's derived from flags on status labels, so the API accepts/returns section and status by name and resolves ids internally. The bot never sees uuids.
§3

The Bot API — your 8 items, mapped to this codebase

Item 1 — the token (the foundation)

  • Authorization: Bearer sow_live_<random> on new /api/bot/v1/* routes. A valid token replaces the Origin check (machines have no Origin header) — this is more secure than today's lane, not less.
  • Token shown once at creation (Admin → Users → "Generate API token"); stored only as a SHA-256 digest; the UI shows sow_live_…ab4c; revocable per token; the user's live role is re-checked on every request, so archiving sow_bot kills its token instantly.
  • Every write through the token is attributed server-side as "SOW Bot - Aboud" — the first attribution in the app that a client cannot fake.

Items 2–3 — read & write endpoints

EndpointWhat it does
GET /api/bot/v1/board?section=&status=&coordinator= Filtered projects with resolved names, stars, coordinator, install date (from records), days-in-status (computed from the activity log; falls back to last-updated when history is past the 5,000 cap — the response says which). Honours ETag → a no-change poll costs ~0 bytes.
GET /api/bot/v1/projects/:idOne row + its full Updates thread + its activity slice.
GET /api/bot/v1/requirements · /match-report The requirements boards; the match report's pure computation moves server-side (it's already a pure function).
POST /api/bot/v1/projects Create with coordinator: null honoured, sourceUrl + requestedBy stored (item 5), and a fuzzy duplicate check: "antony torres" vs "Anthony S Torres" scores ≥85 and returns 409 {duplicates:[…]} unless force: true. Advisory philosophy, same as the rest of the app.
PATCH /api/bot/v1/projects/:id Status / pre-design status / coordinator by name; returns the changed row; stale-data conflict → 409 instead of a silent lost write.
POST /api/bot/v1/projects/:id/updatesNote authored as the token user, with Slack permalink.

Item 4 — audit + one-call undo

  • Every bot write carries a batchId and lands in the existing activity log tagged source:'api'. Bulk calls return the batchId.
  • POST /api/bot/v1/changes/:batchId/revert — reverses the logged old→new values, skips any field a human changed since (reported as conflicts, never overwritten), and logs the revert itself. This is the safety valve that makes an admin bot acceptable.
  • Idempotency-Key support: a retried bulk call returns the original result instead of double-writing (webhooks and bots retry — the handlers must shrug).
  • GET /api/bot/v1/changes?since= — the change feed. This also quietly replaces item 6 for a bot that can't receive webhooks (see decision 4).

Items 7–8 — UI hooks & docs

  • Rows already carry data-project-id. We add data-column-id on cells, data-section on section wrappers, a testid on the Updates panel, and an aria-label sweep on icon-only buttons. Research consensus: accessibility-tree-readable UI + stable testids is exactly what browser agents (Grok Bot, Claude-in-Chrome) key on — and it helps human screen-reader users for free. Zero behavior change.
  • /api/docs: a static page listing every endpoint with a curl example using a $SOW_BOT_TOKEN placeholder. No real token ever appears anywhere.
Bot pain points → resolved: scheduled jobs with no browser stop using stale CSVs (read API) · no stable selectors → testids · no batch id → batchId on every bulk call · duplicates → fuzzy 409 · re-render mis-clicks → stable selectors survive re-renders (full churn reduction is a separate, later effort).

Installation Review — table parity

Good news: when Pre-Design became a full table (item 12), the Active table's features were extracted into a reusable FullTable component, and Installation Review was left on the light table deliberately, with a note saying "say the word if you want them too". You just said the word.

  • Effort: small. ~20 production lines in 2 files + ~100 test lines — wire the review table to the same component and options Pre-Design uses. It gains: drag-to-move columns, resize grips, per-column filters, select-all, draggable rows, grouping. It already shares the column layout; it just couldn't author it.

§5

Notifications — what's broken, the options, the plan

What the audit found

  • The bell stores nothing — it recomputes a view over board history on every render. Read-state is one timestamp in one browser's localStorage (survives logout; two tabs disagree; your laptop and desktop never agree).
  • bug Delete notifications can never appear — the project is tombstoned in the same write, and the bell drops events for deleted projects. Nobody is ever told a project was deleted.
  • bug Clicking a notification never opens what it points at — the routing is wired in the bell and thrown away one level up. It just scrolls the board.
  • No targeting: everything is broadcast to all five of you — yet reviewer assignment produces no notification at all ("nothing tells Omar his row changed"), and Slack-captured requests are invisible to the bell.
  • No bell on mobile. No delivery with the tab closed. And it all rides the 847 KB/15s poll.

Options compared (research: GitHub + web, 2026 state)

OptionVerdictWhy
Novu (self-hosted)no Needs MongoDB + Redis + worker containers on an always-on server — we have none.
Novu cloud / MagicBell / Knockno Free tiers cap at 3 team members or ~1k deliveries, then cliff to ~$250/mo. External dependency for ~50 notifications/day is the wrong trade.
react-hot-toast / sonnerpartial Toasts only — in-session feedback, not a notification system.
Roll our own on the existing poll + Blobs + browser Notification API recommended The 15s poll already detects changes; desktop pop-ups need zero new infrastructure while a tab is open (even minimized); a Blobs-backed inbox and Web Push are clean later phases. $0.

The phased plan

  • N1 (this package): fix + target + pop up. Fix the delete and click-through bugs; notify on reviewer and pre-design-status changes and on Slack requests; add an All | Mine toggle (Mine = projects where you're coordinator/reviewer, or replies to you); per-user read-state, cross-tab sync; mount the bell on mobile; and an "Enable desktop notifications" button — browsers require the permission ask to come from a click, and one notification per project replaces the previous (no spam stack). Known Windows gotcha documented in-app: Focus Assist silently swallows banners.
  • N1 rider — the ETag fix. Cuts ~170 GB/month and makes faster polls affordable, which is what makes notifications timely. It was only ever deferred for a collision that no longer exists.
  • N2 (later): a persisted per-user inbox (Blobs store) — per-item read/unread synced across devices, deletable notifications, and an inbox the bot API can write to.
  • N3 (only if needed): Web Push — delivery with the browser closed. Feasible on Netlify-only (research-verified: push is a stateless HTTP POST, no always-on server needed; service worker + VAPID keys + one function). iOS requires Add-to-Home-Screen. Decide after living with N1.

Extra-work privacy — Khaled sees only his own

Live bug found during the audit, independent of Khaled: on mobile, any member can tap a teammate in the Team list and read their complete extra-work log, export it to Excel, and open the overtime-pay calculator for them. The admin guard that desktop has was never added to the mobile screen. This gets fixed regardless of every other decision.
  • Today: the server sends everyone's entries to every client; members see team totals, the payroll summary table, and whole-team exports. All "members can't open others' logs" logic is client-side cosmetics — and on mobile even that is missing.
  • Layer 1 — ship now (client): one filter at the single seam where the data enters the UI. Members' Extra Work screen becomes: their own log, totals, and export — the sidebar roster, payroll table, print block, team Excel and copy-summary all disappear for members in one move. Admins unchanged. Same honest-team model as the rest of the app.
  • Layer 2 — same package (server): the bot-token lane gives the server its first real identity; the extrawork function gains ownership checks on that lane, written once and ready for humans.
  • Honest ceiling, stated plainly: until humans also log in server-side, someone technical with DevTools can still fetch the raw data. Layer 1 solves the actual requirement — colleagues not seeing colleagues' compensation data in the UI. The full fix is the identity work in §7 of the .md (in-house server login, or the already-drafted Supabase migration) — a separate decision, after this package.

What I looked at and rejected (so you don't have to)

IdeaWhy not
Notification SaaS (Novu/Knock/MagicBell)Server requirements or $250/mo cliffs; roll-your-own is ~$0 at this scale (§5).
Webhook-first bot integration (your item 6)The bot is a browser on a VM — it likely can't receive HTTP. The change-feed endpoint gives it the same thing by cheap polling. Webhook stays designed + parked (decision 4).
Storing "days in status" as a fieldDerived data goes stale; computed from the activity log with a documented fallback instead.
New uuid-based API for statuses/sectionsThe bot locates things by visible text today; the API speaks names and resolves ids internally.
Rebuilding the audit logOne already exists (append-only, immutable, capped) — it gets batch ids and server-authored entries, not a replacement.
Hard-blocking duplicatesHouse rule: advisory, never Required. 409 + force flag.
Pulling the full login rework into this packageThe token lane is forward-compatible with both futures (in-house login / Supabase). Deciding it now would stall the bot work.
